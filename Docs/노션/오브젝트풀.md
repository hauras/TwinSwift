# 오브젝트 풀 (TwinSwift)

> 투사체·데미지 숫자·명중 이펙트를 매번 만들고 지우지 않고 다시 쓰기.
> 결과: 버리는 객체 **1발당 4.9개 → 0.3개 (−94%)**, 투사체 생성 **910 → 346 µs (−62%)**, 끊김(상위 1% 프레임) **33 → 21 ms (−36%)**

---

## 1. 개념

### 오브젝트 풀이란
자주 만들고 금방 버리는 객체를 **미리 만들어 두거나 다 쓴 것을 버리지 않고 모아 두었다가** 다시 꺼내 쓰는 방식.

| | 풀 없음 | 풀 있음 |
|---|---|---|
| 쏠 때 | 새로 생성 (메모리 할당, 컴포넌트 등록, 충돌 등록, 이펙트 생성) | 쉬고 있는 것을 꺼내서 위치만 옮기고 켬 |
| 끝날 때 | 삭제 → 나중에 GC가 정리 | 숨기고 꺼서 풀에 넣음 |
| 비용 | 생성 비용 + GC 부담 | 꺼내기·초기화 비용만 |

**언제 쓰나:** 같은 종류를 **자주, 많이, 짧게** 쓸 때. 투사체, 데미지 숫자, 명중 이펙트가 딱 그 경우.
**주의할 점:** 다시 쓸 때 **이전 상태가 남으면 버그**가 남. (예: 지난 발의 "이미 맞았음" 표시가 남아 다음 발이 아무것도 못 맞힘)

### 빈 칸 스택 (Free list)
쉬고 있는 객체를 담는 목록. **스택**(마지막에 넣은 것을 먼저 꺼냄)으로 둠.

- 꺼내기 `Pop`, 넣기 `Push` 모두 배열 끝에서 → **O(1)**
- 큐가 아니라 스택인 이유: 방금 반납한 객체를 바로 다시 쓰면 그 메모리가 **CPU 캐시에 남아 있을 가능성**이 큼
- 종류별로 따로 (`TMap<클래스, 스택>`): 화염탄 자리에 검기가 나오면 안 되니까

### 언리얼 GC (가비지 컬렉션)
- 언리얼은 **표시-정리(mark & sweep)** 방식: 루트에서 시작해 **살아 있는 객체를 전부 훑어 표시**하고, 표시 안 된 것을 지움
- 그래서 GC 한 번의 시간은 "버린 객체 수"보다 **"살아 있는 객체 수"**에 더 크게 좌우됨
- 기본 간격 약 61초 + 메모리 상황에 따라 실행. 버리는 객체가 많을수록 더 자주 필요해짐
- **풀의 효과는 "GC 한 번의 시간"보다 "버리는 객체 수"로 보는 게 정확함** (측정하면서 직접 겪은 부분)

### WorldSubsystem
**월드(맵) 하나에 자동으로 하나씩 생기는 관리자 객체.** 맵에 배치할 필요 없고, 맵이 바뀌면 같이 사라짐.

```cpp
USActorPool* Pool = GetWorld()->GetSubsystem<USActorPool>();
```

| 방법 | 문제 |
|---|---|
| 전역 싱글턴 (`static`) | 맵이 바뀌어도 남아서 **이미 지워진 액터를 들고 있게** 됨. PIE 재시작에도 꼬임 |
| 풀 액터를 맵에 배치 | 맵마다 손으로 놓아야 하고 빼먹으면 동작 안 함 |
| 게임모드에 넣기 | 역할이 섞임. 클라이언트에는 게임모드가 없음 |
| **WorldSubsystem** | 풀이 담는 액터(월드 소속)와 **수명이 같음** |

서브시스템 종류: `UGameInstanceSubsystem`(게임 전체) / `UWorldSubsystem`(맵 하나) / `ULocalPlayerSubsystem`(플레이어 한 명, Enhanced Input이 이것)

### 인터페이스로 일반화 (ISPoolable)
처음엔 투사체 전용 풀(`USProjectilePool`)이었다가, 데미지 숫자에도 필요해진 시점에 **어떤 액터든 담는 풀**로 바꿈.

- 풀은 **"언제 꺼내고 언제 넣는지"**만 앎
- **"무엇을 켜고 끌지"**는 액터가 인터페이스로 정함
- 처음부터 일반화하면 과한 설계, **두 번째 쓰임이 생겼을 때** 일반화

```cpp
class ISPoolable
{
	virtual void OnCreatedByPool() {}       // 풀이 새로 만들 때 (BeginPlay 전)
	virtual void OnAcquiredFromPool() {}    // 꺼낼 때
	virtual void OnReleasedToPool() = 0;    // 넣을 때: 숨기고 끄고 상태 비우기
};
```

| 액터 | 꺼낼 때 | 넣을 때 |
|---|---|---|
| 투사체 `ASProjectile` | (쏘는 쪽이 `Launch`) | 숨김, 충돌·이동·이펙트 끔, 타이머 정리, 스펙·관통 기록·유도 표적 비움 |
| 데미지 숫자 `ADamageTextActor` | 보이기, 시간 0부터, 틱 켬 | 숨기기, 틱 끔 |

### 나이아가라 이펙트 풀
엔진에 **이펙트 컴포넌트 풀**이 이미 있음. `SpawnSystemAtLocation`의 `ENCPoolMethod`로 고름.

| 값 | 뜻 |
|---|---|
| `None` | 매번 생성, 끝나면 삭제 (기본) |
| `AutoRelease` | 풀에서 꺼내고, 다 재생되면 **자동으로** 풀에 돌아감 |
| `ManualRelease` | 풀에서 꺼내고, 코드가 직접 돌려줌 |

- 그 자리에 한 번 터지는 이펙트(명중, 폭발, 시전 섬광) → `AutoRelease`
- **붙어서 따라가는 이펙트에는 쓰지 않음**: 풀로 돌아간 뒤에도 붙은 채로 다른 곳에 재사용될 수 있음
- 프로젝트에서는 `USAbilityFunctionLibrary::SpawnOneShotEffect` 한 곳에 규칙을 모음 (`IsFriend`처럼)

### 언리얼에서 알아 둘 것
- **`UPROPERTY` + `TObjectPtr`로 들고 있기**: 그냥 포인터면 엔진이 그 액터를 지웠을 때(맵 전환 등) 풀이 모르고 **지워진 객체를 꺼내 씀**. `UPROPERTY`면 엔진이 참조를 앎
- **컨테이너 안에 컨테이너 금지**: `UPROPERTY() TMap<클래스, TArray<…>>`는 리플렉션이 지원 안 함 → 구조체로 감쌈 (`FSActorFreeList { TArray<…> Items; }`)
- **`SpawnActorDeferred` → 표시 → `FinishSpawning`**: `BeginPlay`가 `FinishSpawning`에서 불려서, "풀이 관리함" 표시를 그 전에 해야 함
- **순간이동**: `SetActorLocationAndRotation(위치, 회전, false(쓸기 안 함), nullptr, ETeleportType::TeleportPhysics)`. 쓸기를 켜면 옮기는 길에 충돌이 생기고, Teleport를 안 주면 물리가 속도를 이어받을 수 있음

## 2. 구조

```
쏘는 쪽:  Pool->Acquire<ASProjectile>(클래스, 위치, 주인, 가해자)
            → InitializeProjectile(스펙) → SetHomingTarget(선택) → Launch()
투사체:   명중 / 수명 끝 → ReturnToPool() → Pool->Release(this)
풀:       Release → OnReleasedToPool() → 스택에 Push (꽉 차면 Destroy)
```

| 파일 | 내용 |
|---|---|
| `Public/Pool/SPoolable.h` | 인터페이스 `ISPoolable` |
| `Public/Pool/SActorPool.h` / `.cpp` | 월드 서브시스템 `USActorPool`: `Acquire<T>`, `Release`, 클래스별 빈 칸 스택, 클래스당 최대 64개, 콘솔 변수 `ts.Pool.Enabled` |
| `Projectile/SProjectile` | `Launch` / `ResetForPool` / `ReturnToPool`, `SetLifeSpan` 대신 타이머 → 반납 |
| `UI/DamageTextActor` | `InitialLifeSpan` 대신 `Tick`에서 시간을 세고 반납 |
| `Ability/SAbilityFunctionLibrary` | `SpawnOneShotEffect` (나이아가라 `AutoRelease`) |

### `Acquire` 흐름
1. 클래스가 비었으면 `nullptr`
2. 그 클래스의 스택에서 꺼냄 — 이미 지워진 것이면 건너뛰고 다음 것 (`while`)
3. 있으면: 순간이동, 주인 설정, `OnAcquiredFromPool` → 돌려줌
4. 없으면: `SpawnActorDeferred` → `OnCreatedByPool`(풀이 관리함 표시) → `FinishSpawning` → `OnAcquiredFromPool`

### 버그가 잘 나는 곳: 상태 초기화
`OnReleasedToPool`에서 하나라도 안 비우면 다음 발이 물려받음.

| 안 비우면 | 증상 |
|---|---|
| "이미 처리함" 표시 (`bResolved`) | 다음 발이 아무것도 못 맞힘 |
| 유도 표적 | 화염탄이 이전 어둠 구체의 표적만 맞힘 |
| 쏜 캐릭터 무시 목록 | 계속 쌓임 |
| 반복으로 붙인 이펙트 복사본 | 다음 발에 이전 반달이 붙어 다님 |
| 타이머 | 꺼진 투사체가 나중에 또 반납됨 (두 번 반납) → `bLaunched`로 막음 |

## 3. 측정

### 방법
- 콘솔 명령 `BenchProjectiles 초당발수 초` (또는 실행 인자 `-Bench=60,20 -BenchQuit`)
- 화염탄 초당 60발 × 20초 = 1200발. 가장 가까운 적 쪽 + ±20° **고정 시드** 퍼짐 → 매번 같은 조건
- 단독 실행(`-game`, 1600×900), 시작 3초 뒤 측정 (로딩 끊김 제외), GC 간격 10초 고정
- 잰 것: 투사체 꺼내기 시간(`FPlatformTime`, Insights 구간 `BenchProjectileSpawn`), 프레임 시간(평균·상위 1%·최대), GC(횟수·시간, GC 시작/끝 알림), **새 UObject 수**(`FUObjectCreateListener`)
- **같은 빌드에서** 콘솔 변수 `ts.Pool.Enabled` 0/1만 바꿈 (`-BenchNoPool`) → 코드 경로는 같고 "다시 쓰기"만 꺼짐
- 각 3회

### 결과

| 항목 | 풀 끔 | 풀 켬 | 변화 |
|---|---|---|---|
| 새 UObject (20초) | 5,897개 (1발당 4.9개) | 332개 (1발당 0.3개) | **−94%** |
| 투사체 꺼내기 평균 | 910 µs | 346 µs | **−62%** |
| 프레임 평균 | 16.2 ms | 14.0 ms | −13% |
| 프레임 상위 1% (끊김) | 33.1 ms | 21.3 ms | **−36%** |
| GC 합계 (2번) | 62.3 ms | 50.8 ms | −18% |
| GC 1번 최대 | 30.8~40.9 ms | 25.6~28.2 ms | |

### 문제 → 원인 → 해결
1. **투사체만 풀로 했더니 GC가 그대로**
   - 원인 ①: GC 간격을 10초로 고정해서 20초 측정이면 쓰레기 양과 상관없이 항상 2번
   - 원인 ②: 투사체는 다시 써도 **맞을 때마다 데미지 숫자 액터와 명중 이펙트 컴포넌트가 계속 생성·삭제**됨
   - 해결: 지표를 "새 UObject 수"로 추가 + 데미지 숫자·명중 이펙트도 풀로 → 1발당 4.9 → 0.3개, GC −18%
2. **측정할 때마다 프레임이 13~20 ms로 흔들림**
   - 원인: 측정 중 PC가 다른 일을 함 (다른 프로그램)
   - 해결: 같은 빌드에서 켬/끔을 번갈아 재고, 다른 프로그램을 끄고 3회씩. 흔들림이 큰 숫자는 "경향만"으로 표시
3. **프레임 최대 46~172 ms 튐**: 풀 켬/끔 양쪽에 있어서 풀과 무관 (셰이더 첫 컴파일 등으로 추정, 따로 확인할 것)

## 4. 면접 예상 질문

| 질문 | 답 |
|---|---|
| 왜 스택? | 꺼내기·넣기 O(1), 방금 반납한 것이 캐시에 남아 있을 가능성 |
| 풀이 비면? | 새로 만듦 (풀이 자람). 처음 약 90발까지는 새로 생성 |
| 풀이 끝없이 커지면? | 클래스당 최대 64개, 넘치면 반납 대신 삭제 |
| 두 번 반납하면? | `bLaunched` 표시로 막음 (명중과 수명 끝이 겹칠 때) |
| 꺼낸 게 이미 지워졌으면? | `IsValid`로 확인하고 다음 것을 꺼냄. `UPROPERTY`로 들고 있어서 엔진이 참조를 앎 |
| 왜 WorldSubsystem? | 담는 액터가 월드 소속이라 수명을 맞춤. 싱글턴은 맵 전환·PIE 재시작에서 지워진 액터를 들고 있게 됨 |
| 왜 인터페이스? | 두 번째 쓰임(데미지 숫자)이 생겨서. 풀은 시점만, 켜고 끄는 내용은 액터가 앎 |
| 효과를 어떻게 증명? | 같은 빌드에서 콘솔 변수로 켬/끔, 고정 시드로 같은 조건, 3회. 처음 지표(GC 시간)가 맞지 않아서 "새 객체 수"로 바꾼 과정까지 |
| 멀티에서는? | 피해 적용은 서버 권한에서만 (`HasAuthority`). 클라이언트 표시용 숫자·이펙트는 각자 풀 |
